# MySQL 自动迁移约定

- 每次发布数据库变更前，必须先提升 `application.yml` 中的 `order.migration-version`；`order.version` 是对外展示版本，不作为数据库迁移门禁。
- 新迁移只允许追加，通常使用 `VYYYY_MM_DD_NN__description.sql`。需要在任何 DDL 前执行数据预检时，可在 `src/main/java/db/migration/mysql` 追加同名 Java migration；必须提供 checksum，并保持已发布构建不变。
- 已在任何环境执行过的迁移脚本禁止修改、重命名或删除，否则 checksum 校验会阻止启动。
- Flyway 只扫描本目录；仓库根目录的 `sql/` 不会被自动执行。
- 迁移失败后禁止自动 `repair`。先定位并人工处置失败原因，再按发布流程恢复。
- 空库不能由增量脚本自动初始化，必须先导入经过审核的 `sql/init/order_base_20260803.sql` 受控基线快照；legacy 结构指纹仍取自该 08-03 快照。只有全部 69 张快照表、关键列和主键结构完整且没有历史表时，应用才会采用保守兼容边界 baseline 到 `2026.08.17.0`，08-04/08-08 的历史效果由后续 successor 策略处理。
- `V2026_08_04_00`、`V2026_08_08_00` 必须保留，用于校验已经执行过这些迁移的历史环境；新的无历史 legacy 库不会自动重放它们。
- `V2026_08_18_04` 是不修改 legacy 任务和部门数据的兼容 marker；`V2026_08_18_05` 只幂等补齐缺失的敏感权限及角色关联。两份兼容 successor 一旦执行同样禁止修改或删除。

## 2026-11-08 个人产品匹配比例

- 发布门禁号提升至 `order.migration-version: 1.2.4`，新增 `V2026_11_08_00__member_product_match_ratios.sql`；先完成数据库迁移，再放行使用新列的后台查询和接单请求。
- 迁移仅为 `order_user` 增加可空的 `product_match_min`、`product_match_max`，不回填会员等级比例，不改历史产品匹配开关。两列都为空的历史启用会员仍沿用全局匹配规则。
- 个人开关继续使用 `0=启用、1=禁用`。显式启用或修改比例须满足 `0 < 最小比例 <= 最大比例 <= 100`；仅修改其他会员资料时兼容历史空比例。禁用可保留空值或 `0/0`。
- 新代码已经读取这两列，不能在未迁移的库上直接启动后关闭迁移。回退旧应用时可保留新增列，无需删除列。

## 2026-11-09 会话、身份和并发修复（1.2.5）

- `V2026_11_09_00__identity_indexes_and_link_batch_sequence` 在任何 DDL 前检查 `order_user` 的用户名、手机号、邀请码重复（按数据库排序规则比较，忽略 NULL，不忽略空字符串）。发现冲突立即失败，不删除、不合并、不改名；先人工核对，再按现有发布流程恢复，禁止自动 repair。
- 增加上述三列各自的唯一索引，以及会员上级、最近登录、订单全状态时间列表、提现全状态时间列表索引。保留原状态索引和历史联合唯一索引，避免改变其他查询路径。
- 新增 `order_link_batch_sequence` 并从历史最大批次号初始化。通过独立序列连接池分配并提交编号；业务回滚允许跳号。部署时先停止旧版本写入，禁止新旧批次号生成方式混跑。
- Java migration 对自身编译后的 class 计算 CRC32。发布后应复用相同构建产物；修改源码或更换编译器重新构建可能改变 checksum，应新建后续迁移，不应 repair 覆盖已执行记录。
- 会员鉴权的 Redis/数据库故障返回 HTTP 503（可重试），真正无效/过期的令牌仍返回 401。超过 1 秒的已鉴权 API 请求记录路径、用户 ID、HTTP 状态和耗时，不记录令牌或查询参数。固定三天有效期和单账号重新登录使旧会话失效的策略保持不变。
- `/member/orderuser/giftAmount` 必须携带 `requestId`（16–64 位字母、数字、下划线或短横线）。接口返回持久化结果 `data.state=SUCCEEDED/FAILED`；结果查询沿用 `/member/orderuser/transaction/status/{requestId}`。超时或刷新不得新建编号；Vue 赠送弹窗已配套保存并复用原请求。前后端需配套发布。
- 商品就近价格查询改为先定位最高可用价格，再用同价商品最小 ID 决胜，保持原选择规则并避免候选商品的混合方向排序。
- 真实数据库测试仅允许显式指定本机专用 `codex_backend_hardening_test`；绝不可把业务数据库传入测试。
